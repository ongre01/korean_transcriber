# Korean Transcriber — 다중 마이크 녹음 통합 전사 기능 개발 사양서

- 문서 상태: 신규 기능 제안안 (구현 완료 문서가 아님)
- 작성일: 2026-10-23
- 적용 대상: Qt Widgets + qmake(C++17) GUI, Python 기반 Whisper/OpenVINO 전사 엔진
- 기존 문서: `Qt_Widgets_음성_녹음_전사_UI_개발_사양서.md`, `사용_및_구조_가이드.md`
- 관련 논문: https://arxiv.org/abs/2312.09746

## 1. 목표와 범위

동일 회의를 **서로 다른 마이크/녹음 장치**로 동시에 녹음한 음성 파일을 복수 선택하고, 파일 간 시차 및 장기 녹음 시계 드리프트를 보정한 후, 발화 단위 또는 단시간 구간에서 음성 인식에 적합한 녹음 채널을 선택해 하나의 전사 입력을 생성한다.

기존 단일 파일 처리, 실시간 녹음, Whisper STT, 화자 분리, JSON Lines 프로토콜을 유지한다. **초기 개발은 오프라인 다중 파일 처리**로 한정하며, 여러 물리 마이크를 동시에 실시간 캡처하는 기능은 포함하지 않는다.

```
[녹음 파일 A]  [녹음 파일 B]  [녹음 파일 C]
      \             |             /
       └────────────┼────────────┘
                    ↓
       파일 유효성 및 메타데이터 검사
                    ↓
     디코드 · 공통 샘플레이트로 리샘플
                    ↓
     기준 녹음에 대한 시간 정렬/드리프트 보정
                    ↓
       VAD 기반 발화 구간 및 음질 분석
                    ↓
        구간별 최적 채널 선택
                    ↓
       전환 지점 보정 · 합성 WAV 생성
                    ↓
       기존 Whisper + 선택적 화자 분리
                    ↓
           TXT / SRT / 선택 이력
```

## 2. 연구 배경 및 적용 수준

Bingshen Mu 외, *Automatic channel selection and spatial feature integration for multi-channel speech recognition across various array topologies*, arXiv:2312.09746 (ICASSP 2024).

논문은 attention 기반 coarse-grained / fine-grained channel selection(CGCS/FGCS), MFCCA에 cosIPD 공간 특징 통합, U-Net 유사 convolution fusion을 제안한다. CHiME-7 자료에서 **oracle segmentation**을 사용하는 실험을 수행했으며, 보고된 Eval Macro DA-WER의 **40.1% 상대 감소는 ROVER를 포함한 전체 시스템 결과**다. 이 수치를 아래 제안하는 간단한 전처리 알고리즘의 기대 성능으로 해석하면 안 된다.

본 사양의 **V1(휴리스틱 선별)**은 위 논문의 학습 기반 신경망을 재구현하는 것이 아니다. '다중 채널 중 유리한 입력을 구간별 선택'이라는 목표를 참고한, 기존 Whisper 전단에 독립적으로 붙일 수 있는 실용적 1차 구현이다. **V2(학습 기반)**에서 논문의 FGCS/CGCS 또는 유사 방식을 검토한다.

논문 원문: https://arxiv.org/html/2312.09746v1

## 3. 사용자 시나리오

1. **기존 파일 열기**에서 **다중 마이크 파일 가져오기**를 선택한다.
2. 동일 회의의 2개 이상 녹음 파일을 선택하고 마이크 별칭을 변경한다.
3. 기준 채널(자동 선택 또는 수동)을 지정한다.
4. **시간 정렬 분석**을 실행하고 추정 오프셋, 드리프트, 신뢰도를 확인한다. 낮은 신뢰도인 파일은 오프셋을 직접 보정하거나 제외한다.
5. **음질 분석**을 실행하고 타임라인에서 구간별 우수 채널을 확인한다.
6. 필요시 채널을 강제 선택하거나 자동 결과를 수정한 후 **통합 음성 생성 및 전사 시작**을 실행한다.
7. 일반 단일 파일 처리와 동일하게 전사/화자 분리 결과를 확인하고 TXT/SRT와 진단 메타데이터를 저장한다.

## 4. 입력 제약 및 검증

- 최소 2개 파일, 초기 UX 권장 최대 8개 파일(기술적 제한이 아닌 권장 초기 상한). 기존 지원 확장자 WAV/MP3/M4A/AAC/FLAC/OGG/MP4 유지.
- 각 파일의 길이, 채널 수, 샘플레이트, 디코드 가능 여부를 `engine/audio_metadata.py` 또는 확장된 검사 계층에서 확인한다.
- 원본 샘플레이트·채널 수가 달라도 처리 가능해야 한다. 원본 파일은 수정하지 않는다.
- 한 파일이 스테레오/멀티채널이면 초기 버전에서는 **파일당 모노 신호 하나**로 처리한다. 변환 방식을 기록하고, 차후 원본 채널 별 선택을 지원한다.
- 적어도 공통으로 겹치는 유효 음성 구간이 있어야 자동 정렬할 수 있다. 신뢰할 수 없는 경우 임의 정렬을 강행하지 않는다.
- 녹음 장치 위치에 따라 일부 발화가 한 파일에서만 들릴 수 있다. 이를 단순한 평균 에너지 차이로 판단하지 않는다.

## 5. 시간 정렬 알고리즘

### 5.1 기준 시간축

기준 파일을 선택한다. 통합 결과의 타임스탬프는 이 기준 파일의 시간축을 따른다. 파일의 생성 시각(EXIF 등)은 참고값이며 정확한 동기화 근거로 단독 사용하지 않는다.

### 5.2 초기 오프셋 추정

- 원본을 먼저 디코드하고 임시 분석 샘플레이트(권장 16 kHz)로 통일한다.
- 동일한 발화/특징이 존재하는 창을 찾아 채널 간 정규화 상호상관, 필요 시 GCC-PHAT로 시차를 추정한다.
- 여러 시간창과 복수 후보 피크를 비교해 일관된 지연값을 사용한다.
- 상관 피크 품질과 시간창 간 편차로 `confidence`를 계산한다.
- 소리의 전파시간(마이크 위치 차이) 및 반향 때문에 샘플 단위 완전 일치를 기대하지 않으며, 음성 세그먼트 기준의 실용적 시간 정렬을 목표로 한다.

### 5.3 장기 녹음 드리프트

서로 다른 장치의 오디오 시계가 조금씩 다를 수 있으므로 처음/중간/끝의 여러 앵커에서 오프셋을 측정한다. 일관된 선형 드리프트가 있으면 시간축 affine 보정, 시간에 따라 변화하면 안정성이 검증된 구간별 보정을 사용한다. 드리프트 보정은 재생 속도/리샘플 과정에서 오디오 품질 손상이 최소가 되도록 한다.

### 5.4 실패 처리

- 동일 이벤트를 찾지 못한 파일: 수동 오프셋 요구 또는 해당 파일 제외.
- 공유 구간이 지나치게 짧음: 자동 정렬 불가 표시.
- 정렬 오차가 큰 파일: 품질 평가 대상에 넣기 전에 경고.
- 마이크별 누락 시간: 점수 부여 대상에서 제외(무음 패딩을 실제 녹음으로 취급하지 않음).

## 6. 구간별 음질 평가

### 6.1 구간 설정

- 추천 초기값(논문의 실험 파라미터가 아닌 **본 구현 제안값**): 분석 창 3초, 이동 간격 1초.
- VAD를 이용해 음성 구간을 확인하며, 가능하면 발화 경계를 기준으로 채널 전환 시점을 조정한다.
- 기존 `engine/vad.py`의 발화 검출 기능을 재사용/확장하되 다중 채널 간 음성 검출 결과를 조합해 **한 마이크에만 들리는 발화**도 고려한다.

### 6.2 품질 특징

| 특징 | 목적 | 주의 사항 |
|---|---|---|
| 발화 검출/음성 존재 | 발화가 실제로 수집된 채널 우선 | 음량이 큰 잡음을 발화로 오판하지 않기 |
| 추정 SNR | 음성 대비 배경 잡음량 | 무음/비정상 잡음 환경에서 추정 불안정 가능 |
| 클리핑 비율 | 찌그러진 녹음 감점 | 압축 오디오의 샘플 피크만으로 판단할 수 없음 |
| 음성 명료도 대리 지표(선택) | 먹먹함/반향 등 반영 | 계산량과 지표 신뢰도 검증 필요 |
| 채널 유효성 | 파일 누락, 음소거, 매우 작은 신호 제외 | 낮은 레벨 자체가 곧 낮은 음질은 아님 |

모든 특징을 동일한 범위로 정규화하고, 명확한 결함(클리핑/녹음 끊김)에 패널티를 부여한다. 초기 점수 가중치는 설정값으로 격리하며 검증 데이터로 보정한다. 단순 RMS/음량 최대값 선택은 금지한다.

예시 점수 정의(확정 공식 아님):

```
score(mic, interval)
    = w_snr * snr_score
    + w_speech * speech_presence_score
    + w_clarity * clarity_proxy_score
    - w_clip * clipping_penalty
    - w_loss * invalid_interval_penalty
```

### 6.3 채널 선택·합성

- 음질 차이가 작으면 이전 마이크를 유지하는 **히스테리시스**를 적용해 빈번한 전환을 억제한다.
- 최소 유지 구간(초기 제안: 2~3초)을 둔다. 다만 다른 채널에만 발화가 잡히는 예외에서는 전환을 허용한다.
- 음성 중간 전환을 피하고 가능한 한 무음 구간/발화 경계를 우선한다.
- 전환부에서 실제 샘플 정렬이 확인된 경우에만 짧은 crossfade를 고려한다. 서로 다른 위치에서 녹음한 신호는 위상 차이로 comb filtering을 만들 수 있으므로 기본적으로 무조건적인 합성/평균은 금지한다.
- 모든 마이크가 불량인 구간도 삭제하지 않는다. 가장 유효한 원본을 사용하되 경고와 신뢰도 저하를 표시한다.
- 출력 길이와 타임스탬프를 보존하며 원본 파일을 그대로 보관한다.

## 7. 기존 시스템 연동

기존 가이드가 명시한 책임 분리를 유지한다.

```
Qt GUI
 ├─ gui/mainwindow.*
 ├─ gui/input/MultiAudioInputDialog.*  [신규 제안]
 ├─ gui/input/MultiAudioInputModel.*   [신규 제안]
 ├─ gui/backend/TranscribeOptions.h    [확장]
 ├─ gui/backend/BackendProcess.*       [확장]
 └─ gui/backend/BackendEvent.h         [프로토콜 확장 시 동시 변경]
            │ QProcess, JSON Lines
            ▼
Python
 ├─ engine/backend_bridge.py          [확장]
 ├─ engine/multimic/align.py            [신규]
 ├─ engine/multimic/quality.py          [신규]
 ├─ engine/multimic/select.py           [신규]
 ├─ engine/multimic/pipeline.py         [신규]
 ├─ engine/vad.py                       [재사용/확장]
 ├─ engine/transcribe_npu.py            [기존 전사 재사용]
 └─ engine/diarization.py               [기존 화자 분리 재사용]
```

권장 방식: **통합 음성을 단일 16 kHz mono WAV로 임시 생성**한 후 기존 `transcribe_npu.py`에 입력한다. 기존 단일 파일 처리 로직 변경을 최소화할 수 있다. 필요한 경우 원본 파일과 선택 이력을 결과 폴더에 별도 저장한다.

**참고:** 제공된 `codegraph.db`는 함수/파일 인덱스를 포함하지만 원본 소스코드 전체가 아니므로, 이 문서는 실제 소스 패치를 완료했다는 의미가 아니다. 인덱스에서 `engine/backend_bridge.py`, `engine/backend_protocol.py`, `engine/vad.py`, `gui/backend/BackendEvent.h` 등의 존재를 확인했다.

## 8. 명령행 및 프로토콜 변경안

기존 `--input <single-file>`은 그대로 둔다. 새 인자 `--multi-input-manifest <json>`을 상호 배타 옵션으로 추가한다.

매니페스트 예시:

```json
{
  "version": 1,
  "inputs": [
    {"path": "D:/meeting/mic_A.wav", "label": "테이블 중앙"},
    {"path": "D:/meeting/mic_B.m4a", "label": "발표자 근처"},
    {"path": "D:/meeting/mic_C.wav", "label": "참석자 근처"}
  ],
  "reference_index": 0,
  "alignment": {"mode": "auto", "manual_offsets_ms": {}},
  "selection": {"mode": "automatic", "window_seconds": 3.0, "hop_seconds": 1.0}
}
```

`manual_offsets_ms`는 GUI에서 설정된 파일 인덱스별 보정값을 기록하는 확장 필드로 정의한다. 스키마 검증/잘못된 경로 검사/상호 배타 인자 검증은 Bridge에서 수행한다.

확장 상태값 제안:

- `aligning_audio`
- `assessing_channels`
- `selecting_channels`
- `rendering_merged_audio`

완료 메시지는 기존 `text_file`, `srt_file`을 유지하며, 다중 입력 모드에서는 `merged_audio_file`, `alignment_file`, `selection_file`을 추가할 수 있다. **새 이벤트·필드를 실제 도입할 때는** `engine/backend_protocol.py`, GUI `BackendEvent.h`, 계약 문서 `engine/backend_protocol.md`, 각종 테스트를 동시에 변경한다. stdout은 기존과 같이 JSON Lines 전용, stderr는 진단 로그 전용으로 유지한다.

진행률은 전처리/전사/화자 분리/저장 단계로 나누되, 단계별 실행 시간 예측이 불안정할 수 있으므로 `progress.value=null` 또는 단계 표시를 허용한다. 취소는 기존 `BackendProcess` 정책을 그대로 활용하되 불완전 임시 파일을 정리하고 원본은 보존한다.

## 9. 결과 저장

```
outputs/meeting_001/
 ├─ merged_16k_mono.wav        # 최적 채널 선택 후 단일 입력
 ├─ alignment.json            # 채널별 오프셋, 드리프트, 신뢰도
 ├─ channel_selection.json    # 구간별 선택 채널, 점수, 품질 정보
 ├─ result.txt
 └─ result.srt
```

`channel_selection.json`에는 `start`, `end`, `selected_input_index`, `quality_score`, `reason/confidence` 등을 기록한다. 모든 타임스탬프는 정렬된 기준 시간축을 사용한다. 원본 경로와 원본의 해시를 남기면 재현성 검증에 유리하다(파일 내 민감정보/개인정보 표시 정책 준수).

## 10. GUI 제안 (Qt Widgets)

- 입력 방식: `단일 파일` / `실시간 녹음` / `다중 마이크 파일`.
- 다중 파일: `QFileDialog::getOpenFileNames()`로 복수 선택, 파일 테이블에 `사용`, `파일`, `길이`, `마이크 별칭`, `정렬 오프셋`, `신뢰도`, `상태` 표시.
- 버튼: `파일 추가`, `제거`, `시간 정렬 분석`, `음질 분석`, `통합 음성 미리 듣기`(재생기 지원 시), `전사 시작`.
- 분석 결과: 마이크별 시간축과 구간별 선택 현황. 초판은 테이블 위주, 추후 파형/타임라인으로 확장 가능.
- 모든 동작은 UI 메인 스레드에서 블로킹하지 않는다.
- 기존 단일 파일 모드를 기본 상태로 유지하고, 다중 모드는 옵션으로 제공한다.

## 11. 검증 시나리오와 수용 기준 제안

| ID | 시나리오 | 수용 기준(초기 목표) |
|---|---|---|
| MM-01 | 동일 음성에 인위적 ±0.5초 시차 부여 | 충분한 공통 발화가 있을 때 추정 오차 20ms 이하를 목표로 테스트 |
| MM-02 | 재생 시간 차이가 누적되는 장치 시계 차이 | 30분 이상 합성 테스트에서 시차 추정/보정 후 오차를 측정하고 미달이면 경고 |
| MM-03 | 파일 A에만 구간 잡음 추가 | 잡음 구간에서 B를 우선 선택하는지 확인 |
| MM-04 | B에 clipping 추가 | 해당 구간에서 B의 점수가 내려가는지 확인 |
| MM-05 | A에서만 말하는 참석자 존재 | A의 발화가 통합 결과에서 사라지지 않는지 검증 |
| MM-06 | 파일마다 녹음 시작/종료 시각 상이 | 유효 중첩/비중첩 구간 보존, 누락을 무음으로 잘못 채점하지 않음 |
| MM-07 | 상관관계 없는 다른 녹음 파일 혼입 | 낮은 동기화 신뢰도 경고 및 자동 통합 차단/명시적 제외 |
| MM-08 | 단일 파일 모드 회귀 테스트 | 기존 결과 및 JSON 프로토콜 정상 동작 |
| MM-09 | 처리 중 취소 및 실패 | Qt 응답성 유지, 입력 보존, 임시 파일 정리, 정확한 상태 전환 |
| MM-10 | 전사 품질 A/B 비교 | 단일 최적 파일 전사 대비 CER/WER, 누락 발화 수, 화자 오류를 실제 한국어 회의 데이터로 평가 |

위 수치(예: 20ms)는 **검증 목표**이며 실측 성능을 보장하지 않는다. 실사용 녹음 간 음향 차이, 반향, 대화 중첩이 심하면 오차가 더 커질 수 있다.

## 12. 단계별 개발 순서

**Phase M1 — 입력/정렬:** 복수 파일 UI, 메타데이터 검사, 오프셋 추정, 신뢰도/수동 정렬, 합성 테스트.

**Phase M2 — 음질 선택:** VAD 기반 통합 음성 구간 검출, SNR/클리핑 등 평가, 히스테리시스/발화 경계 전환, `merged_16k_mono.wav`와 선택 이력 저장.

**Phase M3 — 전사 연동:** Bridge 인자/프로토콜/Qt 검증 확장, 기존 Whisper 및 화자 분리 재사용, 상태·취소·결과 표시 통합.

**Phase M4 — 품질 개선:** 실제 회의 녹음 비교 평가, 드리프트 고도화, 다중 화자 동시 발화 보완, 학습 기반 채널 선택/분리 실험.

## 13. 제한 및 후속 과제

- **단일 최적 채널 선택은 다른 마이크에만 들리는 작은 음성, 동시 발화를 누락할 수 있다.** 특히 화자 겹침(오버랩) 시 단순 선택으로 모두 보존할 수 없다.
- 완전한 다중 채널 음성 융합은 후속 단계에서 beamforming/음원 분리/채널별 STT 결과 병합 등을 별도로 검토한다.
- 논문의 neural channel selection 및 spatial feature integration을 도입하려면 별도 학습 모델, 의존성, 실험 설계가 필요하다. 기존 OpenVINO Whisper 추론 코드에 단순 옵션만 추가해서 재현할 수 있는 접근이 아니다.
- 시간 정렬에 실패하면 보수적으로 중지하거나 수동 오프셋을 요청해야 하며, 잘못된 자동 정렬 결과를 정상으로 표시하지 않는다.
