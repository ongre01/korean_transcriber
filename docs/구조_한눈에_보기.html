요약

  • 두 프로세스 구조. Qt/C++ GUI(gui/)는 녹음, 입력 선택, 상태 표시, 결과 표시를 맡습니다. 음성 디코드, 전사, 화자 분리, 다중 마이크 처리는 Python 엔진(engine/)이 처리합니다. 둘은 QProcess로 연결됩니다.
  • 통신 계약. GUI는 backend_bridge.py에 인자 목록을 넘겨 실행합니다. Bridge는 stdout으로 JSON Lines 이벤트를 보내고 stderr로 진단 로그를 남깁니다. 계약 문서는 engine/backend_protocol.md입니다.
  • 입력 3종, 실행 경로 하나. 단일 파일·녹음·다중 마이크 입력은 모두 16 kHz mono 신호로 바뀐 뒤 같은 전사·저장 경로를 탑니다. 다중 입력은 먼저 정렬·채널 선택을 거쳐 merged_16k_mono.wav 하나로 합쳐집니다.
  • 전사 엔진 2종. 기본 엔진은 Whisper(OpenVINO GenAI, NPU/GPU/CPU)입니다. Nemotron(외부 nemo-speech.exe, GGUF)도 고를 수 있으며 이 기능은 아직 커밋되지 않은 작업 트리 변경입니다.

전사 실행 흐름

아래 칩은 Bridge가 보내는 state 이벤트 값이고 실제 전송 순서대로 놓았습니다. 점선 칩은 옵션을 켰을 때만 나옵니다.

단일 입력 (기존 파일 또는 녹음 WAV) — --input PATH
preparing→ decoding_audio→ detecting_speech→ loading_model→ transcribing→ diarization→ saving_result→ completed

점선: detecting_speech는 무음 건너뛰기가 켜졌을 때, diarization은 --diarization일 때. 함수 경로: run_bridge → _run_single_input → _transcribe_and_save

다중 입력 (마이크 여러 개) — --multi-input-manifest JSON
preparing→ multimic.run_multi_audio_preprocessing() — 각 단계 progress=null decoding_audio→ aligning_audio→ detecting_speech→ assessing_channels→ selecting_channels→ rendering_merged_audio → 통합 WAV를 다시 디코드한 뒤 단일 입력과 같은 경로 → completed (+3개 경로)

모델·장치·프롬프트 확인은 긴 전처리 전에 preparing에서 끝냅니다. 통합 WAV를 디코드한 길이가 기준 시간축과 다르면 오류로 중단합니다. 함수 경로: run_bridge → _run_multi_input → _run_multi_audio_preprocessing → _transcribe_and_save

엔진 분기 (_transcribe_and_save 안)

Whisper (기본) — _transcribe_whisper
detecting_speech (VAD)→ loading_model→ transcribing→ diarization

무음만 있는 입력은 경고를 보내고 모델 로드와 화자 분리를 건너뜁니다. VAD를 쓰면 발화 구간별로 따로 전사하고 원래 시간축을 유지합니다.

Nemotron미커밋 — _transcribe_nemotron
loading_model→ transcribing

별도의 VAD나 diarization 상태가 없습니다. 화자 분리는 네이티브 CLI에 내장되어 있습니다. 요청 길이 상한(기본 29분)을 넘으면 균등 구간으로 나눠 순서대로 처리하며, 진행률은 구간이 끝날 때마다 갱신됩니다.

세그먼트 이벤트는 화자 분리가 끝난 뒤에만 나갑니다. 화자가 없는 임시 세그먼트를 먼저 보냈다가 다시 보내는 일은 없습니다(_transcribe_and_save 주석에 명시된 계약).

다중 마이크 전처리

입력 하나를 기준으로 삼아 나머지를 그 시간축에 맞추고, 구간마다 음질이 가장 좋은 마이크를 골라 16 kHz mono WAV 하나로 이어 붙입니다. 어떤 입력도 단독으로 전사하지 않습니다. 아래 수치는 코드의 기본 설정값입니다.

디코드·준비

decoding_audio
  • 입력마다 16 kHz mono 분석 신호와 유효 구간 마스크를 만듦
  • 파일 지문(SHA) 기록, 입력별 실패를 모아서 한 번에 보고
  • 입력 2개 이상. GUI 권장 상한은 8개이고 백엔드에는 상한이 없음
pipeline.py · prepare_multi_audio_inputs

시간 정렬

aligning_audio
  • 기준 입력의 창(0.75 s, hop 0.25 s, 최대 8개)마다 NCC와 GCC-PHAT로 상관 피크를 찾음
  • ±20 ms 안에서 합의한 관측치로 affine 적합 → 오프셋과 드리프트(ppm)
  • 탐색 범위는 ±2 s이고, 실패한 입력만 ±30 s로 한 번 더 탐색
  • 수동 오프셋이 있으면 자동 추정을 대신함(드리프트 보정 없음)
align.py · AlignmentConfig, apply_manual_alignment_offsets

발화 검출

detecting_speech
  • 정렬된 모든 입력에 VAD를 실행
  • 정렬 후 신호를 기준 시간축으로 warp한 다음 분석
quality.py · analyze_aligned_speech

음질 평가

assessing_channels
  • 30 ms 프레임 단위로 SNR, 클리핑, 무효 구간, 내부 공백, 잡음을 측정
  • 가중치: 유효성 0.15 · 발화 0.30 · SNR 0.55 (0~30 dB 정규화)
  • 패널티: 클리핑 0.65 · 무효 0.35 · 공백 0.25 · 잡음 0.35
quality.py · QualityScoringConfig, score_aligned_quality

채널 선택

selecting_channels
  • 창 3 s, hop 1 s (GUI가 매니페스트에 넣는 값)
  • 히스테리시스 0.05, 최소 유지 2.5 s로 잦은 전환을 막음
  • 전환 경계는 ±0.5 s 안의 발화 구간 경계로 이동
  • 사용자 override는 해당 구간에만 적용하고 다른 구간의 자동 선택은 바꾸지 않음
select.py · ChannelSelectionConfig, select_channels

합성·진단 출력

rendering_merged_audio
  • 기본은 하드 컷. 위치가 다른 마이크를 섞으면 위상 차이로 comb filtering이 생길 수 있기 때문
  • crossfade는 옵션이며 경계에서 샘플 정렬이 확인될 때만 적용
  • 출력: merged_16k_mono.wav, alignment.json, channel_selection.json
pipeline.py · MergedAudioConfig, write_multi_audio_outputs
GUI 다이얼로그의 "음질 분석"(multimic_quality.py)과 실제 전사는 같은 함수 plan_multi_audio_selection()으로 선택 계획을 만듭니다. 따라서 같은 매니페스트라면 사용자가 검토한 계획과 전사에 쓰이는 계획이 같습니다(backend_protocol.md "다중 입력 실행 경로").

GUI에서 다중 입력을 준비하는 순서

  1. 파일 추가: MultiAudioInputDialog::chooseFiles를 실행하면 파일마다 AudioFileInfo가 audio_metadata.py로 검사합니다.
  2. 기준 입력 지정: 기준 콤보로 고르며 매니페스트의 reference_index가 됩니다.
  3. 정렬 분석: startAlignmentAnalysis가 multimic_alignment.py를 실행합니다. 실패한 입력에는 editManualOffset으로 수동 오프셋을 넣을 수 있습니다.
  4. 음질 분석과 채널 검토: startQualityAnalysis가 multimic_quality.py를 실행합니다. 결과는 5 s 격자의 검토 행으로 표시되고, 행 단위 override를 적용할 수 있습니다.
  5. 전사 시작: MultiAudioManifestFile이 임시 매니페스트 JSON을 쓰고, BackendProcess가 --multi-input-manifest로 Bridge를 실행합니다.

녹음 파일은 AppDataLocation/recordings/recording_YYYYMMDD_HHMMSS.wav에 저장됩니다. WAV 헤더 마무리와 commit이 성공해야 완료로 처리됩니다.

MultiAudioFiles

다이얼로그에서 정렬이 해결되어야 전사 시작이 허용됩니다(hasResolvedMultiAudioAlignment). 해결은 자동 정렬이나 수동 오프셋 중 하나로 됩니다.

GUI–Python 계약

계약의 기준 문서는 engine/backend_protocol.md(버전 1)입니다. GUI와 Bridge 양쪽이 스트림을 검증합니다.

스트림 규칙
  • stdout: UTF-8(BOM 없음) JSON 객체를 한 줄에 하나씩 쓰고 매번 flush
  • stderr: 로그, traceback, 네이티브 라이브러리 출력. Bridge가 fd 1을 stderr로 돌려 섞이지 않게 함
  • 성공하면 completed가 정확히 1회 마지막에 오고 종료 코드는 0
  • 실패하면 error가 정확히 1회 마지막에 오고 종료 코드는 0이 아님
  • 알 수 없는 type이나 state, 필수 필드 누락, 종료 이벤트 뒤의 데이터는 프로토콜 오류
인자 전달
  • QProcess::setProgram()과 setArguments()로 개별 전달하며 shell 문자열을 조합하지 않음
  • --input과 --multi-input-manifest 중 하나만 필수
  • Whisper 쪽 인자: --device, --model-dir, --window-seconds 등
  • Nemotron 쪽 인자: --engine nemotron, --nemotron-executable, --nemotron-model, --nemotron-config

취소 순서

  1. GUI의 BackendProcess::cancel()이 stdin에 cancel 한 줄을 쓰고 terminate()를 호출합니다. Windows에서는 terminate()가 콘솔 프로세스에 전달되지 않으므로 stdin 경로가 실제 취소 수단입니다.
  2. Bridge의 CancellationWatcher가 0.1 s 간격으로 stdin을 확인하다가 cancel을 받으면 주 스레드에 KeyboardInterrupt를 보냅니다. 그 뒤 staging을 정리하고 error와 함께 코드 130으로 끝납니다.
  3. 네이티브 추론 때문에 2 s 안에 Python으로 돌아오지 못하면, 감시 스레드가 staging을 직접 지우고 종료 이벤트 없이 130으로 끝냅니다.
  4. GUI는 유예 시간 3 s가 지나면 kill()합니다. 취소를 요청한 뒤 받은 이벤트는 무시하고 결과를 취소로 처리합니다.

결과 파일 게시

실패하거나 취소된 작업은 최종 이름의 파일을 만들거나 덮어쓰지 않습니다. 이 동작을 engine/result_staging.py의 ResultStaging이 보장합니다.

출력 폴더에 .transcribe_XXXXXXXX.partial 또는 .multimic_XXXXXXXX.partial 생성 + .owner.lock→ 모든 결과 파일을 그 안에서 완성→ 정해진 순서로 최종 이름으로 이동→ completed 이벤트
  • 게시 순서: alignment.json → channel_selection.json → merged_16k_mono.wav → SRT → TXT. 사용자가 여는 TXT가 마지막입니다.
  • 이동 중에 실패하면 이미 옮긴 파일을 되돌리고 덮어쓴 이전 파일을 복원합니다.
  • 강제 종료로 남은 staging 폴더는 잠금이 풀려 있으므로, 같은 출력 폴더를 쓰는 다음 실행이 지웁니다.
  • 결과 이름은 <입력 stem><suffix>.txt/.srt입니다. 다중 입력이면 merged_16k_mono<suffix>.txt/.srt입니다.
